# Icon libraries and icon-design approaches for a SimHub DDU (Super Formula SF23 / iRacing, 1280x517, SVG -> 2x PNG pipeline), researched 2026-10-25

Method note: GitHub API (`gh`) was not enabled for this session, so library facts come from README pages (WebFetch), `raw.githubusercontent.com` file-existence checks (HTTP 200/404 on specific icon paths), and jsDelivr package listings (file counts per npm version). Icon counts below are counted SVG files in the named npm release unless stated. Pinterest and Dribbble could not be read (see question 4).

## Q1. Which open-source icon sets best suit a dark, monochrome, technical/motorsport UI? (licence, count, variants, relevant glyphs)

### Takeaway
For a rasterise-once pipeline the strongest candidates are Material Design Icons by Pictogrammers (7,447 glyphs, the only mainstream set with real automotive glyphs such as `tire`, `racing-helmet`, `car-brake-temperature`, `car-speed-limiter`, `car-traction-control`, `flag-checkered`), Phosphor (6 weights incl. duotone, `tire`, `flag-checkered`, `gas-pump`), Tabler (6,238 icons incl. `steering-wheel`, `engine`, `gas-station`, `flag-3`, `helmet`) and Lucide (clean 2px-stroke UI set with fuel/gauge/wind/weather but no tyre or engine). For weather, Meteocons v3 (519 glyphs x 4 styles incl. a single-colour `monochrome` style, MIT) is the best match. Only Remix Icon needs a licence flag: its licence changed in January 2026 from Apache-2.0 to a custom "Remix Icon License v1.0".

### Inferences
- Stroke vs fill matters for the Grafite look: Lucide/Tabler/Iconoir are live-stroke sets (2px / 2px / 1.5px at 24), so stroke can be set to any value before rasterising; Phosphor and MDI are pre-outlined fills, so thickness is chosen by weight file (Phosphor) or fixed (MDI). Phosphor weights are visible from the geometry: bold uses 12-unit end-cap radii on the 256 grid, consistent with a 24/256 stroke (about 2.25px at 24); the thin/light/regular/bold values (about 0.75/1.1/1.5/2.25px at 24) are my reading of the Phosphor design and were not confirmed from a doc.
- Phosphor duotone (second layer at 20% opacity) maps directly onto a "tile one step lighter than background" palette: the tint layer can be recoloured to the tile colour step (#181B1F-like) or accent at low alpha during SVG preprocessing.
- A mixed approach is realistic: MDI or Phosphor for tyre/helmet/flag/brake glyphs, Meteocons for weather, hand-drawn for the existing trend/wind/position arrows. Keep one family per panel to stay coherent.
- Because Python stdlib-only code produces the .djson but icons are produced once by headless Chromium, any library works as long as the SVG files are vendored into the repo with their licence text; licence compatibility is the only blocker (Remix's new licence is permissive but custom; Game-icons needs credits).

### Gaps
- No verified glyph list for Remix Icon, Carbon, Font Awesome Free, Fluent; Lucide `tire`/`engine` not tested.
- Exact Phosphor weight stroke values and Material Symbols' current glyph count (2,500+ vs 3,800+) not reconciled from a primary source.

## Q2. Motorsport-specific icon sets (racing flags, tyres, pit lane, DRS/push-to-pass, ERS) on GitHub or marketplaces?

### Takeaway
No open-source, permissively licensed icon set specifically covering racing flags + tyre compounds + pit lane + DRS/ERS was found. Racing-specific sets exist only on commercial marketplaces (Elgato Marketplace, Gumroad, Creative Market) with unclear redistribution terms, so the practical open route is to compose motorsport glyphs from MDI/Phosphor/Tabler (tyre, helmet, checkered flag, brake temperature, speed limiter) and draw the missing ones (pit lane, DRS, OTS, flag colours) by hand in the existing Grafite style.

Creative Market, Gumroad, SVGRepo](https://www.svgrepo.com/vectors/racing/)

### Inferences
- Pit lane, DRS/Overtake System, ERS and flag-state glyphs have no open equivalent: on a graphite UI the cleanest convention in real cars is text/abbreviation inside a shape (e.g. a rounded square with "PIT", "OT", "DRS") rather than a pictogram, which also matches the existing typographic language (Arame Mono uppercase). This is a design inference, not a sourced fact.
- Marshal flags are best built as simple flag silhouettes with one flat colour each (yellow, blue, red, white, green, black, checkered via MDI/Phosphor) because colour carries the meaning, in line with the dashboard's "one accent per meaning" rule.
- Commercial packs should only be used as inspiration unless the seller's licence explicitly allows redistribution inside a freely shared dashboard.

### Gaps
- Elgato/Gumroad licence terms for redistribution are not stated on the pages fetched.
- No GitHub repository for F1 tyre-compound or flag icons was found; a deeper GitHub code search was not possible (API access disabled).

## Q3. What do real F1/Super Formula/Formula E wheel displays, iRacing UI and popular SimHub dashes use for icons? Icon vs text at a glance.

### Takeaway
The actual SF23 wheel display documented by iRacing is text-label based (LAP, TIME, REF, DIFF, SPEED, FUEL, ECT, EOP, OT Left, ReTime, TMS FL/FR) with a green gear box, colour overlays and a 3-LED cluster; icons are not part of the real car's language. Popular SimHub dashes (TWF Dash, Lovely-style dashes) emphasise per-wheel tyre/damage graphics. The evidence supports mixing: short uppercase labels for values, small pictograms only for categorical state (weather, tyre, damage).

### Cited Findings
- iRacing's SF23 manual: the wheel has an integrated digital display with four pages (Engine, Overtake, TMS, Tire Temps). Engine page fields are LAP, TIME, REF, DIFF, a gear indicator "in a green box", SPEED, FUEL (fuel burned), CAL POT POSITION (throttle shaping in orange), ECT (coolant temp) and EOP (oil pressure). Overtake page replaces ECT/EOP with OT Left and ReTime. TMS page shows tyre pressures (TMS FL, TMS FR...). — [SF23 manual PDF](https://s100.iracing.com/wp-content/uploads/2023/09/Super-Formula-SF23-Manual-V2.pdf)
- SF23 Overtake System states are signalled by colour rather than icons: active = green overlay with a countdown timer and bar (turns red when under 20 s); reset = blue/red bar on left plus LEDs flashing purple; available = LEDs blue. The left LED cluster also shows brake temperature (green LEDs low/top). — [SF23 manual PDF](https://s100.iracing.com/wp-content/uploads/2023/09/Super-Formula-SF23-Manual-V2.pdf)
- Real F1 wheels: central display for speed, lap time, delta, energy and tyre pressure, with top lights for revs/DRS and side lights repeating flags; a "P/PIT/PL" pit-limiter button. Formula E: nothing found. — [Ferrari SF90 wheel](https://www.ferrari.com/en-BG/magazine/articles/ferrari-sf90-formula-one-steering-wheel)
- iRacing's own HUD (2026 seasons): new Sim UI widgets added in 2026 S3 (Track Map, Fuel Calculator, Incident Tracker), Tire Compounds update, Pit Summary and Car Damage widgets in 2026 S4. Visual style of these icons was not described in any source found. — [boxthislap S3 notes](https://boxthislap.org/iracing-2026-season-3-release-notes/); [racinggames.gg S4 2026](https://racinggames.gg/article/iracing-season-4-2026-update-live-new-cars-track-scans-ui-overhaul)
- TWF Dash (a SimHub family "inspired by the Lovely Dashboard") shows tyre data split into inner/middle/outer sections and per-wheel damage where the game supports it; the Lovely Dashboard forum thread I found only discusses tyre temp/wear display behaviour, not its icons. — [overtake.gg search result summary](https://overtake.gg/downloads/twf-dash-universal-ecosystem-ams2-iracing-acc-ac-rf2-and-more.55413); [simhubdash.com thread](https://www.simhubdash.com/community-2/simhub-support/f1-2024-lovely-dashboard-tire-display)
- A RaceDepartment F1 dashboard lists tyre damage/temperature plus a weather report "in 5 and 10 minutes"; another lists session weather and wing damage as percentage. — [raycerray F1 wheel dashboard](https://www.racedepartment.com/downloads/raycerray-f1-wheel-dashboard.61849/)
- Driver-distraction rule of thumb: NHTSA 2013 voluntary guidelines cap single glances at 2 s and total eyes-off-road per task at 12 s (road-car context, secondary tasks). — [Strickland NHTSA speech](https://www.nhtsa.gov/sites/nhtsa.gov/files/strickland-distraction_guidelines_03122012.pdf); [dashboardsymbols.com summary](https://dashboardsymbols.com/2013/04/two-second-rule-distraction-guidelines-seek-to-limit-eyes-on-text/amp/)
- Commercial SimHub/Stream Deck ecosystems (DashForge, 4Sim, Simagic MagicDash) rely on dark backgrounds, colour-coded warnings and gauge-style widgets. — [DashForge](https://apps.apple.com/id/app/dashforge/id6772732368); [4Sim](https://dropcone.itch.io/4sim-telemetry); [Simagic MagicDash 4](https://simracewebshop.com/a/p/products/simagic-magicdash-4)

### Inferences
- Since the real SF23 wheel uses short uppercase labels and colour fields, keeping the dashboard's labels as the primary carrier and adding icons as secondary redundancy (never icon-only for numbers) mirrors the car and the existing Arame Mono language.
- Icons earn their place where a word is long or ambiguous (weather state, damage location, flag state, tyre) and where the same accent colour carries meaning; for fuel/temperature/pressure the label text (FUEL, ECT, EOP) is faster than a pictogram.
- The "temporary state panels" (Damage, Lap Review, Weather, New Lap Info) are glanced at in a different regime (pit/yellow/lap end) than the main race page, so they tolerate richer, larger illustration-style icons than the main page.

### Gaps
- I could not open the Lovely Dashboard GitHub/RaceDepartment page, TWF Dash pages (HTTP 403), RSS or DahlDesign pages, so their actual icon styles are unverified.
- No source found on Formula E display icons or on the visual style of iRacing's new Sim UI icons.
- Behavioural evidence (icon vs text recognition time in racing) was not found; the University of Twente sim-racing dashboard theses (essay.utwente.nl 95989 and 94366) exist but their text was not retrievable.

## Q6. Legibility best practices for small icons on a screen viewed at distance (pixel grid, minimum size, stroke width at 1x/2x, optical sizing)

### Takeaway
Sources agree on the mechanics (integer viewBox, strokes aligned to the pixel grid, even stroke widths, optical size/grade adjustments for light-on-dark) but no authoritative racing-specific minimum exists; the practical method is to compute size from a visual-angle formula for the actual viewing distance and to choose stroke widths that land on whole device pixels after the 2x raster.

### Cited Findings
- Optical size (Material Symbols opsz 20-48 dp) automatically adjusts stroke thickness so symbols look consistent across sizes; for light symbols on dark backgrounds Google recommends low grade (-25) to reduce glare, and high grade (up to 200) for emphasis. — [Google Fonts Material Symbols guide](https://developers.google.com/fonts/docs/material_symbols)
- Pixel alignment: a 1 px stroke centred on an integer coordinate straddles two pixels and renders soft; centring on half-pixel coordinates renders crisp; fractional stroke widths (e.g. 4.567) blur; even widths can sit on a pixel boundary; unrounded viewBox coordinates made 1 px lines blurry; rendering at a larger export scale reduces blur. — [WHATWG list thread on blurry lines](https://lists.whatwg.org/pipermail/whatwg-whatwg.org/2013-August/082722.html); [Penpot pixel alignment thread](https://community.penpot.app/t/pixel-alignment/341); [Readme blog "Precision With Every Pixel"](https://blog.readme.com/precision-with-every-pixel/)
- ISO 15008:2017 covers in-vehicle visual display legibility: minimum contrast ratio, character dimensions and stroke-width-to-height ratio (actual values not available in the snippet; the standard is paywalled). — [ISO 15008:2017 catalogue](https://iteh.es/catalog/standards/iso/d07adfe7-f551-4557-bb09-7236d8491cf6/iso-15008-2017)
- Amazon's automotive guideline: minimum icon size 12 mm, touch target 18 mm, minimum text x-height 4 mm; a UX article assumes ~60 cm eye-to-screen and suggests 5.3-6 mm minimum text height (about 34-38 px at 160 dpi), flagging the assumption. FHWA gives symbol height = distance x tan(visual angle). — [Amazon Fire TV automotive UX](https://developer.Amazon.com/docs/fire-tv/automotive-ux-guidelines.html); [uxdesign.cc 11 heuristics](https://uxdesign.cc/11-heuristics-for-ux-in-automotive-ac6ab9a8783c); [FHWA](https://www.fhwa.dot.gov/publications/research/safety/03065/11.cfm)
- Brand icon guides typically use a 2 px primary stroke (1.5-2 px at 24) with 1 px detail strokes on a 64 px grid; these are practice, not legibility standards. — [Motorola Solutions iconography](https://brand-guidelines.motorolasolutions.com/iconography); [IONITY iconography](https://ci-dev.ionity.eu/assets/iconography)
- Library defaults that matter at 2x: Lucide/Tabler 2 px at 24 px grid, Iconoir 1.5 px, Phosphor six selectable weights, Meteocons monochrome ~2 px at 128 px grid. — see Q1 sources.

### Inferences
- For 2x rasterisation, design/choose the icon at the displayed size S px but export a PNG of 2S: a 24 px displayed icon from a 24-grid SVG with a 2 px stroke yields 4 device px lines at 2x (even, crisp); a 1.5 px stroke (Iconoir) yields 3 device px (still integer, acceptable); icons authored on a 256 or 128 grid (Phosphor, Meteocons) must be scaled so the stroke is still a whole number of device pixels, otherwise render at the exact target pixel size.
- Because SimHub may scale the PNG if the Image element's width/height differ from the PNG's displayed size, the safest approach is to rasterise at exactly 2x the component size and keep the component an integer number of pixels; this avoids runtime resampling blur. SimHub's resampling behaviour was not verified here.
- On a 517 px-high screen viewed from a typical wheel distance (the viewing distance was not given), practical minimums are likely about 20-24 px for glance icons and 32 px+ for state-critical ones, with 2 px strokes or heavier at that size; thin weights (Phosphor thin/light, Iconoir 1.5) will disappear at distance. These are rule-of-thumb inferences from the visual-angle approach, not sourced numbers.
- Light-on-dark icons look bolder than dark-on-light at the same stroke (irradiation), supporting Google's low-grade recommendation: favour regular rather than bold weight and avoid pure white (#FFF) icons; use a dimmed off-white or an accent colour.

### Gaps
- No source found for SimHub's image scaling filter or for recommended icon sizes on 1280x517 DDU screens.
- ISO 15008 numeric limits and any F1/GT-specific dash legibility studies were not accessible.

## Candidate evolution paths (inputs for the three proposals)

### Takeaway
Three distinct, licence-safe directions emerge: (A) a unified stroke icon system from Lucide or Tabler (consistent, MIT/ISC, fits comb-bar crispness), (B) a filled/duotone system from Phosphor or MDI with real tyre/helmet/flag glyphs plus Meteocons monochrome for weather, and (C) a "typographic badge" system that keeps hand-drawn glyphs for categorical state and uses boxed text labels (PIT, OT, DRS) as the dominant icon language, as on the real SF23 wheel.

### Cited Findings
- Path A material: Lucide (ISC, 2,171 glyphs, 2 px strokes, includes fuel/gauge/wrench/thermometer/wind/cloud-rain-wind/trending/triangle-alert) and Tabler (MIT, 5,184 outline + 1,054 filled, adds `steering-wheel`, `engine`, `helmet`, `gas-station`, `flag-3`, `car-crash`). — see Q1 sources
- Path B material: Phosphor (MIT; thin/light/regular/bold/fill/duotone with `tire`, `flag-checkered`, `gas-pump`, `engine`, `steering-wheel`, `wrench`); MDI (Apache-2.0; `tire`, `racing-helmet`, `car-brake-temperature`, `car-speed-limiter`, `car-traction-control`, `car-sports`); Meteocons v3 `monochrome`/`line` weather (MIT, 519 glyphs, wind-direction-* and wind-beaufort-* included). — see Q1 sources
- Path C material: SF23 manual shows the car's own display language is uppercase labels + colour overlays + a green gear box + LED colour states (green/blue/purple/red). — [SF23 manual PDF](https://s100.iracing.com/wp-content/uploads/2023/09/Super-Formula-SF23-Manual-V2.pdf)

### Inferences
- Path A (stroke family, "Technical line"): vendor ~25 SVGs with a script that normalises stroke to a 2 px grid-aligned width and recolours via `currentColor`; weather could stay with Lucide glyphs or switch to Meteocons `line`. Lowest risk, highest coherence with chamfered tiles; weakness is no tyre/engine in Lucide (Tabler fills the gap with a different but compatible 2 px style).
- Path B (filled/duotone, "Solid instrument"): Phosphor duotone (or fill) with accent colour on the tint layer; Meteocons monochrome for weather; richer and more "automotive HMI"; risk is heavier visual weight against the thin-lined comb bars, and duotone alpha must be baked in the raster.
- Path C (typographic badge, "Race-control language"): keep hand-drawn pictograms only for weather/trend/wind; elevate flags, pit, OT, DRS to chamfered pill/tile badges with Arame Mono text and the accent colours already defined; zero library dependency, most faithful to real SF23 and F1 wheels, least icon-licence exposure.
- Hybrids are natural: C for state badges + A or B for the four temporary panels (Damage, Weather) where larger illustrative icons help.
- All paths stay within the existing pipeline: vendor SVG -> normalise (stroke/colour/viewBox) -> Chromium raster at 2x -> versioned PNG; no layout changes needed if PNG pixel dimensions match the current Image elements.

### Gaps
- Layout geometry (icon slot sizes in px) was not available to the researcher, so size recommendations are generic; the actual slot sizes in the repo should drive the stroke/weight choice.
